## 二、今后企划（用户定了以后再做）

| 事 | 说明 |
|---|---|
| **一两个字母的短查询提速** | 单字母且按匹配度排序时约 1.5 秒，两字母 0.05–0.4 秒；慢的主要是单字母 + `searchrank`。vndb 官方也是照样 `LIKE '%a%'`。方向：保持子串语义（汉字单字照样能搜），按类型缩小扫描（分区或部分索引，105 万行里作品只占 24 万），短词排序不算相似度。动手前先 `EXPLAIN ANALYZE` 确认耗时在哪 |
| **拼写容错** | vndb 官方没有。做法：精确结果少于阈值时，用现有 trigram 索引另查一段"Close matches"，与精确结果分开显示；只对 ≥4 字符启用，两个阈值进环境变量。"只有一条结果就跳转"已经做了 |
| **本地边缘走 HTTP/2** | 本地 Caddy 是 `auto_https off`，浏览器只在 HTTPS 下用 HTTP/2，于是同一地址只有 6 个连接，镜像还没取过的封面会占满连接（跳转时取消旧页图片已缓解）。根治是本地开 `tls internal`，代价是本地地址改成 https、浏览器要信任 Caddy 的根证书，`start.ps1`、e2e 的 baseURL、端口说明都要改。上线若本来就在 HTTPS 后面，已是 HTTP/2 |

## 四、明确不做

| 事 | 为什么 |
|---|---|
| 按自己的列表 / 评分筛选（"在我的某个列表里"、"我打过 ≥4 分"） | 用户 2026-10-03 定。要读 API 与用户服务配合；若将来要做，倾向前端先取自己的 id 列表再作为 `id=` 传给读 API（受 1000 个 id 上限约束），而不是让读 API 直连用户库 |
| 多目标语言 | 用户 2026-10-17 定：译文只做一种目标语言，原文开关保持二元 |
| musicserve、logserve、procserve | 旧项目里的服务。不做音频目录；NeoVNDB 不记搜索日志；一共五个进程，`start.ps1` 够用 |
| 机器翻译接口 | 旧的 `/translate` 一直回 501，从未接过后端 |
| 写回 vndb；导入用户资料、评论、单条投票 | 只读镜像 |
| 随机背景图 / 随机图 | 用户 2026-09-26 定 |
| 图片服务与边缘挡住被挡图片的直接访问 | 全年龄模式下读 API 不给出被挡图片的地址，知道地址的人仍能打开；用户决定暂不处理 |
| 标签排行在全年龄下重算 | 标签与特征的条目数用的是 vndb 自己的 `c_items`，全年龄下的数字会比列表多（含被挡的作品） |
| 给服务端渲染的内容加入场动画、`loading.tsx` | 会推迟本来首帧就有的东西；页面数据一次取完，加 `loading.tsx` 反而先闪一屏骨架 |
| 管理页能改监听地址、目录、连接池、缓存后端、请求上限 | 改它们要重建对象，重启更诚实；用户服务的备份与扫会话间隔一年改不了一次，不值得也加一套 |

## 五、做过的取舍

这些不是待办，是为了让后来的人知道为什么是现在这样。

**搜索与筛选**

- **条件表达式写在地址里**（`f=`，紧凑语法，可读可手改，与旧项目的 `,` `+` `()` 一脉相承），而不是一份 JSON；扁平参数继续有效，与 `f=` 是"且"。
- **关联嵌套不另写编译器**：查询层把每个关联筛选编译成一个 `EXISTS`，嵌套只是在里面递归调用关联类型自己的筛选表。
- **全局搜索挂在 `/q`**：`/s` 已经是人员书架（"字母 = 该类型的书架"是整套地址方案的根基），`q` 不在 vndb 的七个类型字母里。
- **分面计数实时算**，而不是导入时预计算：用筛选本身的条件数，一条语句 8–250ms，结果按代次进缓存；带着其余筛选也能算，比预计算只能给全库数更有用。
- **嵌套在人员里的 `role` 问的是"此人在任何作品里担任过"**，问"在这部作品里"用作品的 `credit=s224:scenario`。

**全年龄模式**

- 开关由管理员控制；未登录的读者始终只看全年龄（相当于 Pixiv 对 R-18 的做法）。暴力也管：图片按暴力投票，作品层面靠 18+ 分级（dump 没有作品级暴力分级，不拿"血腥"之类的标签去挡作品）。
- 做法是应用层的"遮罩"（入库时定级，每个请求在查询构造处统一加条件），而不是 Postgres 的行级安全：后者每个请求要设会话变量，派生查询与统计都要跟着改，出了问题难查。
- 新程序先上、线上代次还没有列表时，遮罩"未就绪"，谁都不遮罩。没有选"未就绪时拒绝访客"：那样补上列表之前整个站对访客都打不开。

**图片**

- 盘上没有的图默认重定向到 vndb：第一次打开快，之后由边缘直出。代价是读者的浏览器直接连 vndb（IP 会被看到；`<img>` 一律 `no-referrer`）、连 vndb 不顺时反而慢、首次被看的图 vndb 出两份流量；302 必须 `no-store`。
- 运行中可改的设置每个服务存一个 JSON 文件、只存与 `.env` 不同的项，而不是存进数据库：图片服务不开数据库，读 API 的库每次换代整体替换。

**导入**

- 派生表的索引在填充前就建好（审查 I4）：挪到派生之后实测派生快约 40 秒，但建索引多约 13 秒、建索引那一步也慢了，不划算。
- 请求跨越换代时，新一代的数据可能存在旧一代的缓存键下（审查 R15）：只影响换代那一刻正在进行的请求，换代后旧键不再有人读；要修得在查询的同一事务里读代次，不值得。

**前端**

- 关系图在不限作品数时卡顿不算问题：作品数上限是上线时设的，开发环境不限时慢是预期的（ELK 布局已在 Web Worker 里，不再为此做更多）。
- 样式：颜色都走变量；`text-xs` 以下只有 `text-2xs` / `text-3xs` 两档；白色半透明底的 0.03 / 0.04 / 0.06 / 0.07 四档各有用处，没有合并。
