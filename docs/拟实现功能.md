## 一、搜索（设计稿，待确认）

目标是比 vndb.org 自己的高级搜索更强。先说现状，再分四层说怎么做。

### 现状（2026-09-23 更新）

| 能力 | NeoVNDB | vndb.org | 旧项目 |
|---|---|---|---|
| 文本搜索 | ✅ 按词拆分、每个词都要命中（规范化子串 + trigram GIN 索引）；双引号内按原序 | 按词拆开、每个词都要命中 | 同 Kana |
| 多词、乱序 | ✅ `ever out infinity` 0 → 2 条 | ✓ | — |
| 错字容忍 | ✗ | ✗ | ✗ |
| 跨类型搜索 | ✅ 顶栏搜索 + `/q` 七类分组结果 | 有 | ✗ |
| 筛选组合 | ✅ `f=` 表达式：`,` OR、`+` AND、`!` NOT、括号 | AND / OR / NOT 任意嵌套 | `,` OR、`+` AND、括号 |
| 取反 | ✅ `!lang=en` 与 `lang!=en` 皆可 | ✓ | ✗ |
| 标签阈值 | ✅ `tag=g749:2.0:1`（最低分、剧透上限）；特征只有剧透 `trait=i568:1` | 最低分 + 剧透上限 | ✗ |
| 关联嵌套 | ✅ `release=(lang=en+freeware=true+platform=win)` | ✓ "有一个发行版同时满足……" | 部分 |
| 个人数据 | ✗ | 按自己的列表/投票筛 | ✗ |

**最严重的那条（关联不能嵌套）已经解决。** 同层对比实测：`release=(lang=en)+release=(freeware=true)+release=(platform=win)`（可由三个不同发行版分别满足）21,465 条，`release=(lang=en+freeware=true+platform=win)`（必须同一个发行版满足）19,724 条——更严格的问法返回更少，正是从前问不出来的那个区别。

### 第一层：文本搜索像人期望的那样工作

### 第二层：可组合的筛选表达式（"更强"的核心）

一棵条件树：`and` / `or` / `not` 节点，叶子是 `[字段, 运算符, 值]`——与 vndb / Kana 的筛选 JSON 同形，老用户不用重学。

- 运算符：`=` `!=` `>=` `<=` `>` `<`
- **关联字段的值可以是一棵关联类型的子树**，而不只是 id：
  ```
  ["release", "=", ["and", ["lang","=","en"], ["freeware","=",true], ["platform","=","win"]]]
  ["character", "=", ["and", ["trait","=","i568"], ["role","=","main"]]]
  ["staff", "=", ["and", ["id","=","s8"], ["role","=","scenario"]]]
  ```
- **标签带阈值**：`["tag", ">=", ["g749", 2.0, {"spoiler": 0}]]`

**为什么这件事在本项目里不贵**：查询层已经把每个关联筛选编译成一个 `EXISTS` 子查询。嵌套只需要在那个 `EXISTS` 里递归调用关联类型**自己已有的**筛选编译——七个类型包的筛选直接复用，不需要为嵌套再写七套。

护栏：深度上限、节点数上限、按条件估价（查询层已经给字段选择估价，推广到筛选即可）、语句超时。

URL 编码（**已定并实现**）：紧凑语法 `f=`，可读可手改，与旧项目的 `,` `+` `()` 一脉相承；扁平参数继续有效，与 `f=` 是 AND 关系。

### 第三层：vndb.org 做不到或没有的

- **按自己的数据筛**："在我的某个列表里"、"不在我任何列表里"、"我打过 ≥4 分"、"我没打过分"。涉及跨服务，需要决定做法（见下方待定）。
- **保存的搜索**与命名预设；搜索历史（仅本地）。
- **分面计数**："语言：英文（12,340）"。实时算很贵，但**镜像每周才变一次**——可以在导入时按代次预计算，这是本项目相对 vndb.org 的结构性优势。
- **相似作品**：按标签分数向量算余弦相似度，同样可以按代次预计算。vndb.org 没有。
- **描述全文检索**（按语言分词）。vndb.org 不搜描述。

### 第四层：界面

- **简单模式**：现在的筛选条，保持不变。
- **高级模式**：条件构建器——条件组、AND/OR 切换、取反、"有一个发行版满足……"这样的嵌套块；旁边是同一棵树的文本视图，给熟练用户直接改。两边编辑的是同一个东西。
- **顶栏全局搜索框**：跨七种类型，每类取前几条分组显示，可键盘操作；回车进完整结果页。
- **全局搜索挂在 `/q`**（用户 2026-09-18 定，已实现）。最初指定的 `/s` 已经是人员书架（`/s` 全部人员、`/s8` 某个人），而"字母＝该类型的书架"是整套地址方案的根基；`/q` 同样只有一个字母，且不在 vndb 的七个类型字母 v r c p s g i 之内。
- 地址即查询。

### 已经在的部分（2026-09-18）

- 顶栏搜索：≥1024px 是输入框，640–1024px 是放大镜图标，<640px 进"书架"菜单——顶栏宽度就这么点，实测加一个 28px 图标会让 800px 下七个书架被切掉 29px，所以书架平铺的断点从 800 提到了 840。
- `/q`：七种类型各问一次，每类最多 6 条，按 `searchrank` 排；某一类答不上来就略过，不连累整页。多的给"All N"链到该类型的列表页。
- 输入完整 id（`v17`、`V17`）直接跳转，不当搜索。
- **条件表达式 `f=`**：`,` 或、`+` 与、`!` 非、括号分组；值含逗号括号空格时用双引号。与扁平参数是 AND 关系，且逗号的含义没变（`lang=en,fr` 与 `f=lang=en,lang=ja` 是同一个问题）。实测三处等价：`f=lang=en+has_anime=true` 等于两个参数（673）；`!!lang=en` 等于 `lang=en`（24,432）；跨筛选 OR 的 35,956 正好是两支之和。条数上限是配置项（`NEOVNDB_MAX_FILTER_NODES`，开发环境为 0）。
- **关联嵌套**：`release=(…)`、`character=(…)`、`producer=/developer=(…)`（vn），`vn=/producer=/developer=/publisher=(…)`（release），`vn=(…)`（character）。括号里写的是**关联类型自己的筛选**，编译时才去问它，所以给发行版新加一个筛选，VN 这边立刻就能用。id 形式一字未改——每个转换过的筛选都和它替换的 SQL 逐条对过（developer p37 = 10、producer p37 = 51、release?vn=v17 = 55 等）。条数预算全请求共享，嵌套不能把它翻倍（实测：允许 3 条时 1 外 + 2 内通过，再加一条被拒）。
- **只能相等的筛选现在会拒绝比较运算符**：`lang>=en` 从前被当字面值静默匹配不到，现在明确报错。

### 跨类型搜索（用户 2026-09-18 指定，排在单类型搜索之后）

"用 p / c / t / …… 去搜 v"：例如按制作方名字搜作品、按角色或标签搜作品。这正是第二层里"关联字段的值可以是一棵子树"的用法——叶子换成关联类型的 `search`：

```
["producer", "=", ["search", "=", "nitroplus"]]
["character", "=", ["and", ["search","=","..."], ["role","=","main"]]]
```

**已做**（2026-09-24）：条件构建器的"有一个……满足"就是"在关联对象里搜"的控件；`/q` 的制作方、人员、角色三段标题旁给出"N 部作品由其中之一开发 / 有其中之一参与 / 由其中之一配音 / 有其中之一登场"的链接（数为 0 不显示；只有一个匹配时措辞换成单数）；制作方、人员、标签、特征四种目录页在标签页右侧给出"Refine in …"，把当前标签页的筛选作为条件带到该类型的列表页，可以继续加条件。人员与声优两个 VN 筛选改成可嵌套（`staff=(search="maeda jun")` → 21 部）。

遗留：嵌套在人员里的 `role` 问的是"此人在**任何**作品里担任过该职位"，不是"在这部作品里"；要问后者需要一个带角色的 VN 筛选（`staff=s224:scenario` 之类）。标签/特征不能按名字嵌套（`tag=(search=…)`），因为它们走的是带阈值的 `Related`；目录页已经覆盖了"这个标签下的作品"。

### 关联类型的字段还没全变成筛选（2026-09-24 盘点）

构建器已经用上了后端**全部**筛选；嵌套进制作方、人员等类型时能问的少，是因为这些类型在后端本来就只有几个筛选。字段有、筛选没有的，按价值排：

| 类型 | 值得加的筛选 | 说明 |
|---|---|---|
| 通用（v / r / p / s） | **外链站点** `extlink=steam` | "在 Steam / DLsite 上有卖"、"有官网"。四个类型都有 extlinks，一个实现四处用 |
| release | **DRM**（无 DRM）、分辨率、动画程度 | "无 DRM 的英文发行版"是很常见的问法 |
| vn | 实测时长 `length_minutes`、关系类型（有续作 / 是 fandisc）、封面内容分级 | 时长比 `length` 档位更准 |
| character | 生日（月 / 日）、有无立绘、是否某角色的变体 | |
| producer / staff | 有无介绍、别名（已由搜索覆盖） | 价值较低 |

另外两个结构性的：人员嵌套里的 `role` 应当能问"在**这部**作品里的职位"（带职位的 VN 筛选）；标签 / 特征不能按名字嵌套（`tag=(search=…)`），目录页暂时顶替。

## 五、长期约束（任何新功能都要过这几条）

- **本地库是一次 dump 的纯函数**：自己的数据（译文、账号、收藏）必须待在生成 schema 之外。
- **不依赖 Kana API**：运行时与导入时都不调。
- **镜像只存原件**：图片逐字节，派生物可整个删掉重建。
- **鉴权在边缘**：新服务不写鉴权代码，只听回环。
- **先量再改**：怀疑有问题先证明它存在。
- **HTTP 200 不等于页面能用**：前端改动要在浏览器里确认水合。
