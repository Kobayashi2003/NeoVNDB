## 一、搜索（设计稿，待确认）

目标是比 vndb.org 自己的高级搜索更强。先说现状，再分四层说怎么做。

### 现状（2026-09-18 实测）

| 能力 | NeoVNDB | vndb.org | 旧项目 |
|---|---|---|---|
| 文本搜索 | 规范化后的**连续子串**匹配，trigram GIN 索引，约 40ms | 按词拆开、每个词都要命中 | 同 Kana |
| 多词、乱序 | ✗ `ever out infinity` → 0 条，`infinity ever` → 0 条 | ✓ | — |
| 错字容忍 | ✗ | ✗ | ✗ |
| 跨类型搜索 | ✗ 只能进某个列表页搜 | 有 | ✗ |
| 筛选组合 | 筛选之间只能 AND；单个筛选内逗号是 OR | AND / OR / NOT 任意嵌套 | `,` OR、`+` AND、括号 |
| 取反 | ✗ | ✓ | ✗ |
| 标签阈值 | ✗ 只按 id，不看分数与剧透等级 | 最低分 + 剧透上限 | ✗ |
| 关联嵌套 | ✗ `release=r123` 只能按 id | ✓ "有一个发行版同时满足……" | 部分 |
| 个人数据 | ✗ | 按自己的列表/投票筛 | ✗ |

**最严重的一条是关联不能嵌套**。`lang=en&freeware=true&platform=win` 现在查的是"VN 的所有发行版合起来有英文、有免费、有 Windows"——这三条可以分别由三个不同的发行版满足。读者真正想问的是"**有一个**发行版同时是英文、免费、Windows 版"，目前问不出来。

### 第一层：文本搜索像人期望的那样工作

1. **按词拆分，每个词都要命中，顺序无关**。这是现在比 vndb.org 差的地方，改动小、收益大，应当最先做。
2. 双引号包起来的片段按原顺序匹配。
3. **排序**：现在的 `searchrank` 取的是该实体**所有**标签里最高的 prio，与匹配到哪个标签无关——凡是有主标题的都同分，几乎不区分。要改成只看匹配上的标签，再叠加 trigram 相似度与"完全相等 / 前缀"加分。
4. **错字容忍**：严格匹配结果很少时，用 trigram 相似度（`%` 运算符）兜底，并明确标出"近似结果"，不和精确结果混在一起。
5. **把译名也建进索引**：搜"アナル"应当能找到对应标签。
6. **直接输入 id 即跳转**：`v17`、`c521`。

### 第二层：可组合的筛选表达式（"更强"的核心）

一棵条件树：`and` / `or` / `not` 节点，叶子是 `[字段, 运算符, 值]`——与 vndb / Kana 的筛选 JSON 同形，老用户不用重学。

- 运算符：`=` `!=` `>=` `<=` `>` `<`
- **关联字段的值可以是一棵关联类型的子树**，而不只是 id：
  ```
  ["release", "=", ["and", ["lang","=","en"], ["freeware","=",true], ["platform","=","win"]]]
  ["character", "=", ["and", ["trait","=","i568"], ["role","=","main"]]]
  ["staff", "=", ["and", ["id","=","s8"], ["role","=","scenario"]]]
  ```
- **标签带阈值**：`["tag", ">=", ["g749", 2.0, {"spoiler": 0}]]`

**为什么这件事在本项目里不贵**：查询层已经把每个关联筛选编译成一个 `EXISTS` 子查询。嵌套只需要在那个 `EXISTS` 里递归调用关联类型**自己已有的**筛选编译——七个类型包的筛选直接复用，不需要为嵌套再写七套。

护栏：深度上限、节点数上限、按条件估价（查询层已经给字段选择估价，推广到筛选即可）、语句超时。

URL 编码：树 → 紧凑字符串，搜索仍然是一个可以分享的地址。现有的扁平参数继续有效，视为一个顶层 `and` 的简写。

### 第三层：vndb.org 做不到或没有的

- **按自己的数据筛**："在我的某个列表里"、"不在我任何列表里"、"我打过 ≥4 分"、"我没打过分"。涉及跨服务，需要决定做法（见下方待定）。
- **保存的搜索**与命名预设；搜索历史（仅本地）。
- **分面计数**："语言：英文（12,340）"。实时算很贵，但**镜像每周才变一次**——可以在导入时按代次预计算，这是本项目相对 vndb.org 的结构性优势。
- **相似作品**：按标签分数向量算余弦相似度，同样可以按代次预计算。vndb.org 没有。
- **描述全文检索**（按语言分词）。vndb.org 不搜描述。

### 第四层：界面

- **简单模式**：现在的筛选条，保持不变。
- **高级模式**：条件构建器——条件组、AND/OR 切换、取反、"有一个发行版满足……"这样的嵌套块；旁边是同一棵树的文本视图，给熟练用户直接改。两边编辑的是同一个东西。
- **顶栏全局搜索框**：跨七种类型，每类取前几条分组显示，可键盘操作；回车进完整结果页。
- **全局搜索挂在 `/q`**（用户 2026-09-18 定）。最初指定的 `/s` 已经是人员书架（`/s` 全部人员、`/s8` 某个人），而"字母＝该类型的书架"是整套地址方案的根基；`/q` 同样只有一个字母，且不在 vndb 的七个类型字母 v r c p s g i 之内。
- 地址即查询。

### 建议顺序

1. ~~按词拆分的文本搜索~~ **已做**
2. 顶栏全局搜索 + `/q` 结果页
3. 条件树：NOT / 跨筛选 OR / 标签阈值
4. 关联嵌套
5. 条件构建器界面
6. 个人数据筛选（先定做法）
7. 分面计数、相似作品、描述检索

### 跨类型搜索（用户 2026-09-18 指定，排在单类型搜索之后）

"用 p / c / t / …… 去搜 v"：例如按制作方名字搜作品、按角色或标签搜作品。这正是第二层里"关联字段的值可以是一棵子树"的用法——叶子换成关联类型的 `search`：

```
["producer", "=", ["search", "=", "nitroplus"]]
["character", "=", ["and", ["search","=","..."], ["role","=","main"]]]
```

所以**不需要新机制**，但要先把单个类型自己的搜索做好。现在只需在界面上**预留位置**：筛选条要能长出"在关联对象里搜"这一类控件，全局搜索结果页要能显示"作为条件使用"的入口。

## 四、明确不做

| 事 | 为什么 |
|---|---|
| **logserve** | 旧项目里是搜索日志表上的开发者工具。NeoVNDB 不记搜索日志 |
| **procserve** | 旧项目要看住 10+ 个进程；NeoVNDB 一共五个，`start.ps1` 加 systemd 够用 |
| **机器翻译接口** | 旧的 `/translate` 一直回 501，从未接过后端 |
| **写回 vndb** | 只读镜像，不改任何来自 vndb 的数据 |
| **导入用户资料 / 评论 / 单条投票** | 同上 |

## 五、长期约束（任何新功能都要过这几条）

- **本地库是一次 dump 的纯函数**：自己的数据（译文、账号、收藏）必须待在生成 schema 之外。
- **不依赖 Kana API**：运行时与导入时都不调。
- **镜像只存原件**：图片逐字节，派生物可整个删掉重建。
- **鉴权在边缘**：新服务不写鉴权代码，只听回环。
- **先量再改**：怀疑有问题先证明它存在。
- **HTTP 200 不等于页面能用**：前端改动要在浏览器里确认水合。
