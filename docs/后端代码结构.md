## 一、总览

NeoVNDB 把 vndb 官方 dump **原样镜像**进本地 Postgres，再在其上封装一层只读 HTTP API。

核心约束（决定了整个代码形状）：

- **本地库是一次 dump 的纯函数** —— 除 dump 内容外不存任何东西，重新导入即完全重建，因此没有迁移、没有增量更新逻辑。
- **不修改任何来自 vndb 的数据**，也不导入 user 信息、评论、单条投票（只保留聚合值）。
- **不依赖 Kana API**：运行时和导入时都不调用，仅在开发期用于人工对数。
- **镜像只存原件**：数据库里 `vndb.*` 是 dump 的逐字镜像，`data/images/` 是图片的逐字节镜像；两边的派生物（`tags_vn_inherit`、`data/images-derived/`）都可以整个删掉重建。

### 数据流

```
dl.vndb.org/dump/vndb-db-latest.tar.zst
        │  internal/dump        下载 + 校验 + 流式解 tar
        ▼
   tar 内的每张表（TSV）
        │  internal/importer    列改写（v17 → 17）后以 COPY text 灌入
        ▼
   schema vndb_next            ← internal/db/ddl/*.sql 建表
        │  internal/db/derive   算 dump 不导出的东西（分数、闭包、搜索索引、c_* 列）
        ▼
   ALTER SCHEMA RENAME         ← internal/db/generation.go，事务内原子换代
        ▼
   schema vndb（线上）
        │  internal/db/sql → sqlc → internal/db/gen   静态查询
        │  internal/api/query                          动态筛选/排序/分页
        ▼
   HTTP :5100                  internal/api
```

**代次（generation）**：`vndb`（线上）/ `vndb_prev`（上一代，用于回滚）/ `vndb_next`（正在导入）。
Postgres 的 `ALTER SCHEMA RENAME` 可以进事务，所以换代是原子的，线上 schema 永远不会处于半写状态。**在线换代也安全**：rename 不改表的 OID，pgx 又默认缓存预编译语句，但 PostgreSQL 会在 schema 改名时让依赖它的缓存计划失效（psql 实测：同一连接、同一预编译语句、执行超过转通用计划的阈值，rename 后返回新表的数据）。

### 3.1 `cmd/neovndb` —— 命令行入口

#### `main.go`

| 声明 | 职责 |
|---|---|
| `usage` | 帮助文本常量 |
| `main()` | 调 `run()`，出错时打印并以非零码退出 |
| `run()` | 装载配置、建 Store、按第一个参数分发到 `serve` / `import` / `db` |
| `runDB(ctx, args)` | `db` 子命令的二级分发：status / init / promote / rollback / drop / verify |
| `status(ctx, store)` | 取 `Store.Status` 并排版输出：各代次、DDL 是否过期、表行数 |
| `initGeneration(ctx, store, code, dumpURL)` | 用内嵌 DDL 建一个空的 `vndb_next` |
| `promote(ctx, store)` | 把 `vndb_next` 换上线；导入未完成时拒绝 |
| `rollback(ctx, store)` | 把 `vndb_prev` 换回来 |
| `drop(ctx, store, schema)` | 删掉指定代次；拒绝删线上那一代 |
| `verify(ctx, store)` | 跑 `Store.Verify` 并逐步打印结果 |

#### `import.go`

| 声明 | 职责 |
|---|---|
| `localCode` | 从文件名里抠出 `vndb-db-2026-08-19.tar.zst` 的日期，正则 |
| `runImport(ctx, args)` | 导入全流程：定位归档 → `CreateNext` → `load` → `Index` → ANALYZE → `Derive` → 统计派生表 → `FinishNext`。顺序是性能关键（先灌数后建索引，派生前先 ANALYZE）。带 `-promote` 时先过熔断 |
| `load(ctx, store, path)` | 建 Importer、接进度回调、返回每表行数 |
| `resolve(ctx, cfg, file)` | 决定用哪个归档：给了路径就用本地文件（校验和从文件算），否则查上游最新版并下载 |

#### `update.go`

| 声明 | 职责 |
|---|---|
| `runUpdate(ctx, args)` | 查上游 → 与线上代次比 → 相同则什么都不做 → 上游更旧则**拒绝倒退**（那是镜像出问题的样子，导进去会丢一周编辑）→ 否则导入并上线 |

**调度和手动是同一条命令**，这是有意的：只在无人值守时跑的更新路径，出问题的时候没人能复现。

#### `check.go`

| 声明 | 职责 |
|---|---|
| `inspect(ctx, cfg, store, force)` | 读两代的行数、跑 guard、打印结论。有异议则返回错误阻止上线，`-force` 可强过 |
| `counts(ctx, store, schema)` | 读导入时记录的行数；派生表缺失时现场统计（旧二进制导入的代次没记过派生计数，否则会被误报成"从没派生过"） |

#### `serve.go`

| 声明 | 职责 |
|---|---|
| `runServe(ctx, args)` | 建 `api.NewServer`，取路由，交给 `api.Serve` 监听 |

### 3.3 `internal/dump` —— 归档层

只认 tar 和 zstd，不认识任何一张 vndb 表。

#### `fetch.go`

| 声明 | 职责 |
|---|---|
| `Release` | 一个上游版本：URL、日期、代码 |
| `datePattern` | 从 URL 里解析日期的正则 |
| `Latest(ctx, latestURL)` | 解析上游最新档案。**两种重定向形态都要处理**：历史上 latest 链接直接指向带日期的档案，现在指向存放它们的目录 |
| `redirectTarget(ctx, from)` | 跟随一跳重定向；不重定向就返回原 URL |
| `newestListed(ctx, indexURL)` | 从索引页挑最新的档案。**只认 `href` 里的名字** |
| `describe(ctx, url, date)` | 用 HEAD 补上大小与发布时间，**并检查状态码** |
| `Download(ctx, rel, dir)` | 下载到目录，返回路径与 SHA256；已存在则跳过 |
| `digest(path)` | 算文件 SHA256 |

#### 上游索引的两个坑（2026-09 实测）

**① 索引页里两处名字会互相矛盾。** 页面上有两张表：「Latest versions」用**纯文本**写着 latest 应该指向哪个档案，「Files」里才是**链接**着的、真实存在的文件。dump 正在发布的当口这两者会不一致——实测「Latest versions」说 `2026-09-09`，但只有 `2026-09-07` 被链接，而 `2026-09-09` 确实 404。所以扫全文取最大值会选中一个不存在的档案，必须只认 `href`。

**② `describe` 不检查 HEAD 状态码的话**，一个只被登记、尚未发布的档案会变成"0 MB、发布于公元 0001 年"，真正的失败要拖到下载时才以一个说明不了原因的错误暴露出来。

#### `archive.go`

| 声明 | 职责 |
|---|---|
| `maxRowSize` | 单行上限 4MB，防畸形输入撑爆内存 |
| `Table` | 归档里的一张表：名字、列名、行迭代器 |
| `Archive` | 打开着的归档，逐个 tar 成员前进 |
| `Open(path, headers)` | 打开 zstd + tar 流，带上预扫出来的列名表 |
| `(*Archive).Close()` | 关闭底层流 |
| `(*Archive).Next()` | 前进到下一张数据表并返回；跳过 `.header` 成员 |
| `Headers(path)` | **预扫一遍整个归档**收集所有 `.header` 成员。必须单独一遍，因为 header 在 tar 里排在对应数据之后 |

#### 需要知道的坑

- `.header` 成员位于其数据表**之后**，所以列名必须先扫一遍才能解释数据。
- `users` 表排在 `tags_vn` **之后**，而 `tags_vn` 要用 `users.perm_tag` 判定投票是否计数，因此投票权也要单独扫一遍（见 importer）。

### 3.4 `internal/importer` —— 灌数层

#### `importer.go`

| 声明 | 职责 |
|---|---|
| `nullField` | COPY text 格式的 NULL 标记 `\N` |
| `Progress` | 每表完成后的回调类型，让 importer 不必知道怎么输出 |
| `Importer` | 池、目标 schema、进度回调、被剥夺标签权限的用户集合 |
| `New(pool, schema, progress)` | 构造；progress 为 nil 时装一个空实现 |
| `(*Importer).Load(ctx, path)` | 主流程：扫 header → 扫投票权 → 逐表 COPY → 返回每表行数 |
| `(*Importer).copyTable(ctx, s, table)` | 单表 COPY：按 spec 决定列顺序与改写函数，逐行重写为 text 格式交给 PG 解析 |
| `(*Importer).plan(s, header)` | 由 spec + 实际表头，算出目标列清单和行改写函数 |
| `(*Importer).tagVoteRow(index)` | `tags_vn` 专用改写：把 `uid` 换成布尔 `counts`（该用户是否有标签权限），不落任何用户信息 |
| `readDeniedVoters(path, headers)` | 单独扫一遍归档，收集 `perm_tag` 为假的用户 id。只有约两百个账号，所以存"黑名单"而不是整张 users 表 —— 未知投票者因此天然计数，与 vndb 的 `LEFT JOIN` 行为一致 |
| `numericID(value)` | `v17` → `17` |
| `splitID(value)` | 多态 id 拆成 `(kind, num)`，供 `images` / `entry_meta` 用 |
| `named(index, fields)` | 把一行按列名装成 map，供 rewrite 函数使用 |
| `quoteAll(columns)` | 给列名加引号拼成 COPY 的列清单 |

**设计要点**：整条链路是 **COPY text 直通** —— 行被重写成 text 格式后交给 PG 自己解析类型，没有逐列的类型转换器。

#### `tables.go`

| 声明 | 职责 |
|---|---|
| `spec` | 单表导入规格。常见情况只填 `ids`（哪些列是 `v17` 式 id）；形状会变的表则填 `columns` + `rewrite` 自建整行 |
| `skipped` | 完全不导的表：用户级明细（ulist、投票明细、rlists）、vndb 自己的帮助页（docs、quotes）、以及 `users`（导入期读、永不落库） |
| `specs` | 42 张表的规格清单 |
| `specFor(table)` | 按表名查规格 |

### 3.5 `internal/db/guard` —— 换代熔断

一次导入可以在机械意义上完全成功却仍然是错的：截断的归档照样能解析，派生步骤的 join 匹配不到东西时**不写任何行也不报错**。而镜像库自己没有可违反的不变量——它有的是**前一代**。

| 声明 | 职责 |
|---|---|
| `Snapshot` | 一代在检查眼里的样子：代次代码 + 每表行数 |
| `Finding` | 一条不该上线的理由 |
| `Check` | `Name()` + `Inspect(live, next) []Finding` |
| `Guard` | 一组检查，`Default(maxLoss, derived)` 给出标准组合 |
| `Shrunk{MaxLoss}` | 某表掉了超过该比例。**vndb 只增不减**（条目是隐藏不是删除，而隐藏的根本不进 dump），所以任何实质缩水都意味着归档被截断或导入中途停了 |
| `Missing` | 线上有、新代次压根没导的表——导入提前结束的样子 |
| `Required{Tables}` | 指定的表不得为空。这是**专为派生步骤准备的**：一个匹配不到东西的派生查询没有别的痕迹 |

**为什么是接口而不是一串条件**：什么算可疑取决于数据。哪个部署额外导了别的东西、或者明知某张表就是会缩，就自己加一个或去掉一个。

行数来自导入时记录进 `import_info.row_counts` 的**精确值**，读回来不花钱。

实测（20260819 → 20260907 真实一周）：全部通过，**不到 1 秒**。反向（拿旧代次当新代次）被拦住并列出 7 条异议。

### 3.8 `internal/api/query` —— 七类型共用机器层

#### 三个核心概念

**字段表（`Table`）**：一个类型的字段面**和**每个字段怎么产生，声明在同一处。校验用的 `Registry` 由它推导，所以"声明了却填不出来的字段"不可能存在 —— `NewTable` 在启动时 panic。

**Source**：收整页而不是单行，批量是结构性保证 —— Source 里根本拿不到"当前这一行"，写不出 N+1。多个字段可以共用一个 Source（`title`/`alttitle`/`titles` 同一次 `vn_titles`），只跑一次。

**Target（继承）**：片段不列子字段，而是**指向另一个类型的名字**。合法子字段 = `Edge ∪ 目标类型的全部字段`。目标类型加字段，所有嵌套它的地方自动可见。类型图有环（vn→character→vn），所以 Target 是字符串，经 catalog 在请求期解析。

#### `field.go`

| 声明 | 职责 |
|---|---|
| `Source[R,T]` | 页级加载器。R 是该类型的 resolver，T 是行 |
| `Nested` | 一个类型被别的类型看见的样子：`Registry()` + `Objects()`。由 resolver 实现 |
| `Field[T]` | `Kind` / `Row`（逐行纯函数）/ `Source` / `Subfields` / `Edge` / `Target` / `Num` |
| `Table[R,T]` | `IDType` / `ID` / `Fetch`（按 id 取基表行，没有它就不能被嵌套）/ `Fields` / `Sources` |
| `NewTable` | 校验并缓存 registry。六种坏配置各有明确 panic 信息 |
| `(*Table).Objects` | 为别的类型渲染本类型的一批 id：`Fetch` 一次 + `Apply` |
| `(*Table).Apply` | 一页行 → 对象。Row 字段先填，等 Source 的先置 nil（保证"请求过的字段一定出现"），再按去重后的顺序跑 Source |
| `(*Table).allColumns` | 展开"整体都要"的选择 |
| `(*Table).sourcesFor` | 本次选择需要哪些 Source，去重并排序（查询顺序可复现） |
| `Edge` | 一条关系行：父 id、目标 id、这条边自带的属性 |
| `Sub` | 某片段内部的选择，经 catalog 展开 |
| `Relate` | 边批量 → 目标类型自渲染 → 边属性覆盖其上。**目标类型和边属性名都从声明反查**，Source 无法与声明不一致。若选择里没有目标自己的字段（如 `fields=tags.rating`），**跳过目标表不读**，直接用关系行上的 id 拼对象 |

#### `fields.go`

| 声明 | 职责 |
|---|---|
| `ParseFields(cat, reg, maxDepth, value)` | 深度上限由调用方传入，来自配置 |
| `FieldDef` / `Registry` | 校验面。`children(cat)` = `Subfields` ∪ 目标类型字段 ∪ `Edge`（**边属性优先**） |
| `Selection` | 一棵树。`All` = 片段被单独点名，意为"目标的全部**列**"——不含嵌套片段，因为每个都要一次查询，且类型图有环不会终止 |
| `ParseFields` / `add` | 逐段下钻校验。`id` 在**每一层**都是隐式的 |
| `Cost` | 每层字段数 × 该层声明的 `Num`，逐层相加。照 Kana 的算法，上限 10 万 |

#### `limits.go`

`Limits` 结构（`PageSize` / `MaxPageSize` / `MaxIDs` / `MaxFieldDepth` / `MaxCost` / `MaxSearchTerms` / `MaxFilterNodes`）+ `DefaultLimits()`。**全部来自配置，0 即无上限。** `Parse` 把它记进 `Request.Limits`，后续阶段（如 `Page` 校验 id 列表长度、`SearchFilter` 校验词数、表达式校验条数）沿用同一份，不会各自为政；它也进缓存 key，否则放宽上限只会把先前的拒绝从缓存里再端出来。

#### `expr.go` —— `f=` 条件表达式

| 声明 | 职责 |
|---|---|
| `ParseExpr(text, budget)` | 递归下降解析成树。`,` 或、`+` 与、`!` 非、括号；值含逗号括号空格时用双引号。`budget` 是整个请求共享的剩余条数（`Budget(n)` 生成，nil 无上限），嵌套里的条件从同一份里扣；另有一道固定的递归深度护栏 `maxExprDepth = 64`——那不是策略，是防止无上限时把本进程的栈交给查询串的作者 |
| `leaf` / `junction` / `negation` | 树的三种节点 |
| `(*Builder).Expr` | 编译成**一条**条件加进 builder |
| 括号作为叶子的值 | `release=(lang=en)`：括号连同里面的文字**整块交出去**，解析器不知道那是关于谁的条件，也不需要知道——由它所属的筛选在编译时去读。找配对括号时**跳过引号内的文字**（含 `\"` 转义），所以 `producer=(search="a)b")` 不会在引号里的 `)` 处截断 |
| `leaf.compile` | 查该类型自己的筛选表，用一个共享 `Args` 的子 builder 跑它，取回条件。**所以新加的筛选不必改这里就能在表达式里用**；`!=` 编译成 `NOT(...)`，于是每个筛选都白得取反；`id` 明确拒绝——它跳过分页，不是条件 |

逗号的含义与从前一致：`lang=en,fr` 是一个筛选两个可接受值，`f=lang=en,lang=ja` 是两个叶子取或，同一个问题同一个答案（实测均 58,459）。

#### `page.go` 的 `SearchTerms`

把搜索词按空白拆开（引号内不拆），每个词各出一条 `EXISTS` 并 AND 起来：词序无关，且**词越多越快**（每个词都在收窄结果）。

#### `catalog.go`

| 声明 | 职责 |
|---|---|
| `Catalog` | 类型名 → `Nested`。全部类型建好之后统一注册 |
| `Check` | 遍历所有 Target，名字对不上就返回 error —— 拼写错误变成启动失败，而不是某次请求 panic |

#### `filter.go` 的两条路

一个筛选要么**匹配**一个值，要么**比较**一个值，代码里分得很清：

- `Match(one)` 是匹配类的唯一写法——它自带列表展开（逗号）和"拒绝比较运算符"。`TextColumn` / `ArrayColumn` / `RelatedID` / `Related` 以及七个类型包里的自定义筛选全部由它构造。这样写是为了**下一个新加的筛选不会漏掉那个拒绝**：从前 `lang>=en` 会被当成一个叫 `>=en` 的语言去找，找不到，看起来像"没有结果"而不是像写错了。
- 比较类（`IntColumn`、日期、身高……）自己用 `SplitComparison` 把运算符拆下来。

`Relation` 是可嵌套的关联：值是 id 就按 id 匹配（与从前同一句 SQL），值是括号就把里面的条件**用关联类型自己的筛选表**编译进那个 `EXISTS`。目标表按该类型的别名 join 进来；嵌套两层会重用同一个别名，SQL 作用域让内层胜出——这正是要的（每个筛选只谈自己那一类），但也意味着若有筛选去够外层的行会静默拿到内层。目前没有这样的筛选，真要有就得按层给别名编号。

`Related` 是标签/特征的连接匹配，可选最低分与剧透上限（`tag=g749:2.0:1`；特征没有分数，`trait=i568:1` 的数字是剧透）。不填时那两个条件**根本不出现在 SQL 里**，所以既有查询一字未改。

#### `page.go` / `convert.go` / `query.go`

与上一版一致：`Builder` + EXISTS 而非 JOIN、`Page`/`PageSpec`/`orderBy`/`SearchFilter`、六个公共值转换、`Request`/`Parse`/`ClientError`。

#### 字段取值方式分类

七个包的 `fields.go` 里**每个字段都带一个取值方式标签**，用来回答「这个字段和真实数据库是什么关系」。图例定义在 `query.Field` 的文档注释上，标签后面跟具体的表名和列名，可以直接拿去和 `ddl/01_mirror.sql` 对。

| 标签 | 含义 |
|---|---|
| `COL` | 本实体主表上的列，原样透出。改过名的会注明原列（`vn.c_length` → `length_minutes`） |
| `CONV` | 主表单列，换了个表示：单位、编码、拆行，或者把某种「没有」写法归一成 null。事实没变，形状变了 |
| `CALC` | 主表多列合成一个值 |
| `DERIV` | **列在主表上，但这一列 dump 里没有**，是导入时从别的表算出来的（`db/derive/*.sql`）。看着像直取，实际是跨表聚合——数字对不上时首先怀疑这一类 |
| `JOIN1` | 值在另一张表，靠本行上的键一对一取回 |
| `LIST` | 值在另一张表，一对多，聚成一个片段 |
| `REL` | 指向另一个实体：目标类型的整个字段面 + 关系表自带的边属性 |
| `MADE` | 库里根本没存这个值，由 id 或配方拼出来——核对它等于核对那个配方 |

**vndb 自己的缓存列算 `COL` 不算 `DERIV`**：`c_votecount`、`c_rating`、`images.c_sexual_avg` 这些是 dump 里就已经算好的，本项目只读不写。`DERIV` 只留给导入自己填的那几列。

**`chars.main` 只有单向**：它从「实例」指向「本体」，所以本体那一侧原本查不到「谁是我的实例」。`character.instances` 就是把这一列从另一头读出来（`WHERE main = ANY(ids)`），边属性 `spoiler` 取的是**子节点自己的** `main_spoil`——「这个角色其实是那个角色的一个版本」本身可能是剧透，实测 1924 行 > 0。处在中间的实例页要拿到兄弟节点，只能再向本体请求一次，前端就是这么做的。

#### 两处字段语义

| 字段 | 说明 |
|---|---|
| `character.sex` / `spoil_sex` / `gender` / `spoil_gender` | dump 把「看上去是什么」和「其实是什么」分成两列存，正是因为后者会剧透前者；`gender` 是独立的自我认同轴，同样带一个 spoil 列。四列原样暴露，由调用方决定在什么剧透等级下给出后半截。<br>**保留 dump 的列名而没有改叫 `sex_spoiler`**：本 API 别处把 `spoil` 列一律改叫 `spoiler`（`chars_alias` / `chars_traits` / `chars_vns` / `vn_tags`），但那些是 0/1/2 的**等级**，这两列装的是**另一个值**，叫 `spoiler` 会误导。<br>后三列可空且**还可能是空串**（`spoil_sex` 有 9 行、`spoil_gender` 2 行、`gender` 11 行），两种写法同义，都经 `blankToNil` 归一成 null |

#### 按标题 / 名字排序

vn、character、release 的标题不在主表上（分别在 `vn_titles` / `chars_names` / `releases_titles`，按语言分行）。`PageSpec.Table` 里挂一条到本语言那行的**一对一 `LEFT JOIN`**，排序表指向 `COALESCE(latin, title)`：

```go
Table: "vn LEFT JOIN vn_titles vt ON vt.id = vn.id AND vt.lang = vn.olang"
"title": "COALESCE(vt.latin, vt.title)"
```

三张被 join 的表主键都是 `(id, lang)`，而 join 把 lang 钉死成单值，所以每行最多匹配一行——**不放大行数**，"关系筛选用 EXISTS 不用 JOIN"那条规则（针对一对多）不受影响。`staff` 一直就是这么做的。

### 3.10 `internal/cache` —— 响应缓存

| 声明 | 职责 |
|---|---|
| `Cache` | `Get` / `Set` / `Name` / `Close` |
| `Key(generation, parts...)` | `neovndb:<代次>:<sha256 前 12 字节>`。**代次在最前面**，所以 `db promote` 之后上一代的 key 全部不可达，不需要手动失效 |
| `Nop` | 关闭时的实现 |
| `Memory` | 进程内 LRU（`container/list`），带 TTL。默认后端：单实例已经能拿到绝大部分收益 |
| `Redis` | 多实例共享时才值得那个依赖。读写失败只当没命中——缓存挂了是延迟问题，不是正确性问题 |

**key 在解析之后才算**（`query/key.go` 的 `Request.Canonical`），因为那时 `Selection` 已经是结构化的树、`Filters` 已经是 map，都能规范排序。所以 `fields=a,b` 和 `fields=b,a` 是同一条。`Limits` 也进 key —— 放宽上限之后，之前被拒的请求应该重新放行，而不是从缓存读回旧的错误。

接在 `handlers.go` 两个 handler 里，**不接在 resolver 内部**：嵌套请求内部的 `Objects` 各自缓存的话，失效逻辑没法推理。

**代次每次请求都读**，不做 TTL 复用。那次读是 0.12~0.18ms（1 行 16kB 的表），而缓存省的是 300ms。曾经用过 10s TTL，实测发现换代之后会出现一段窗口：有的类型已经答新代次、有的还在答旧 key 的缓存——不是"数据旧"而是"数据不自洽"。库不可达时退回上一次读到的代次，否则所有代次的 key 会塌到一起。

实测（`limit=100` × 4 个片段）：**305ms → 1.7ms**。

## 三·五、图片镜像（internal/img）

dump 的 `images` 表只有元数据（kind、num、宽高、内容投票），**一张图都没有**。所以镜像是残的，`internal/img` 补上剩下那半：importer 对数据做的事，它对图片做，区别只是按需单张而不是整包——46 万张里只有被看过的才值得存。

**它和后端其余部分的关系**

| | |
|---|---|
| 复用 | `internal/vndb`（`ImageURL`，分片规则两边必须一致）、`internal/config`（同一份 `.env`） |
| 明确不复用 | `internal/cache` —— 那是 API 响应缓存：内存/Redis、有 TTL、拿代际做键。图片缓存是磁盘、不过期、与代际无关 |
| 完全不碰 | `internal/db`、`internal/api` —— **不开 Postgres**。一次请求自带 `(kind, num)`，无需查表，因此它不知道什么叫代际，promote 和 rollback 对它没有影响 |

**两个目录**

```
data/images/           镜像。上游原字节，只增不改
  cv/12/79412.jpg
data/images-derived/   派生。每档宽度一份，随时可整个删掉
  256/cv/12/79412.jpg
```

宽度是**路径段而非查询参数**，为的是 URL 与磁盘路径同形——反向代理可以用 `try_files` 直接发命中的文件，Go 进程根本不醒。查询参数进不了 `file` 匹配器。

**一次请求**

```
命中 derived → 代理直出（绝大多数）
未命中 → img.Server
   ├─ 镜像有原图？没有 → single-flight 回源，逐字节落盘
   ├─ 源宽 ≤ 请求宽？是 → 原样返回，不落派生（立绘全部如此）
   └─ 否 → 缩放 → 落派生 → 返回
```

**几个约束的来由**

- **宽度白名单**（默认 128/256/512，超出向上取整）：不限制的话每个没见过的数字都是一次解码加一个新文件，循环请求就能填满磁盘且永不命中缓存。
- **像素上限**（默认 4000 万）：封面里有 15158×15189 这种，解一次比在飞的所有请求加起来还贵，拒绝好过慢慢服务。
- **原子写**（临时文件 + rename）：代理会直接从磁盘发文件，它没法问「这个文件写完了没有」。

## 三·六、译文（trans schema）

vndb 的标签与特征**只有英文**：没有"原文"可切回去，所以 `original` 开关在这两类上给出的是本项目自备的译文。这批数据不来自 dump，因此：

- 放在 **`trans` schema**，不在 `vndb` / `vndb_prev` / `vndb_next` 里。换代只 rename/drop `vndb*`，重新导入不碰它。
- **按文本内容做键**，不按 id：`trans.terms` 用规范化后的名字（`trans.Key`：空白折叠、去首尾、小写），`trans.passages` 用同一规范化结果的 sha256。这样新一期 dump 下来无需任何重解析——文本还对得上就命中，改过就不命中（宁可回落英文，也不显示过期译文）。
- DDL 幂等，`db.Open` 时建，因此新库无需额外步骤。

| 项 | 数量 |
|---|---|
| `trans.terms` | 5,700（tag 3,033 / trait 2,667） |
| `trans.passages` | 6,293（tag 2,983 / trait 3,310），约 3 MB |

对当前镜像的覆盖率（2026-09 实测）：tag 名 2,987/3,014、tag 描述 2,976/3,011；trait 名 2,605/3,094、trait 描述 3,286/3,327。

**`internal/trans/markup.go`** 守着唯一的硬约束：描述里的 `[url=..]`、`[b]` 等标记和 `g749` 这种裸 id 是地址不是语言，译文必须一字不差地带着它们（顺序可变，个数与内容不可变）。`trans seed` 先全量校验再写；有一条不过就整份拒绝，不写半份。实测 6,293 条译文全部通过，其中 4,342 条含此类记号。

API 侧是 tag / trait 上的 `translation` 片段（`lang` / `name` / `description`），以及 trait 的 `group_translation`；只查被选中的那一半。实测取译文与不取译文在 v17（203 个标签）上耗时无差别（62–65ms，噪声内）。

## 三·七、用户服务（backend/users）

**独立的 Go module，独立的数据库 `neovndb_users`**。不是镜像旁边的一个 schema——镜像的 schema 每周整个重建，账号跟着一起没了。没有 sqlc，查询都是手写的短 SQL；`schema.sql` 幂等，启动时执行。

```
backend/users/
├── cmd/users/main.go             启动、配置、扫会话的后台循环、import-legacy 子命令
├── internal/config/config.go     环境变量
├── internal/auth/
│   ├── auth.go                   bcrypt 与会话 token；Check 同时认旧格式并回报"该换了"
│   └── legacy.go                 读 Werkzeug 的 scrypt 串（只读不写）
├── internal/store/
│   ├── store.go                  连接池、用户、会话
│   ├── collections.go            收藏夹与条目（含批量删/移，一个事务，保留 marked_at）
│   ├── ratings.go                评分：按 (人, 类型, id) 存，与收藏夹无关
│   ├── legacy.go                 从旧库迁移：只读旧库、单事务、用户名占用就跳过
│   └── schema.sql                users / sessions / collections / marks / ratings
└── internal/api/
    ├── api.go                    路由、signedIn 包装、注册/登录/会话/改密码、/auth/verify
    ├── limit.go                  登录/注册的尝试次数限制（滑动窗口，内存）
    └── collections.go            收藏夹与评分的全部 handler
```

几处值得知道的取舍：

- **`/auth/verify` 是给边缘用的**，回 `X-User-Id` 与 `X-Is-Admin`。别的服务因此一行鉴权代码都不用写。
- **旧密码就地升级**：`auth.Check` 认出 Werkzeug 的 scrypt 就回 `(ok, stale=true)`，登录成功后顺手换成 bcrypt。实测走通（`scrypt:` → `$2a$`）。
- **`Items` 把整个收藏夹交出来**（上限 1000）给读 API 去排序/搜索——这个服务自己做不到，它不认识 VN 是什么。上限就是读 API 的 id 列表上限：1000 个 id 约 5KB 地址、22ms。
- **评分的清除是 DELETE**，不是 0 分："没有意见"不是一个低分。
- **上限都在 `.env`**：尝试次数与窗口、收藏夹页大小与整表上限。0 即无上限——`Items` 的 SQL 为此用 `LIMIT NULLIF($2, 0)`，否则 0 会被当成"一条都不要"。
- **限流分两把尺**：按来源地址、按用户名各计一次。一个攻击者换一堆地址会撞上后者，一个地址试一堆用户名会撞上前者。来源取边缘追加在 `X-Forwarded-For` 末尾的那一项——可信是因为这个端口只有边缘够得着。登录成功即清零。
- **`answer()` 只给收藏夹用**：它的两个具名分支说的都是"没有这个列表"，评分的 handler 因此直接走 `oops`。

## 四、已知缺口

| 问题 | 现状 |
|---|---|
| 别名命名空间无人管 | `PageSpec.Table` 的 FROM 与各筛选里的 EXISTS 共用一套别名，靠手动躲开。release 的 `rt2` 就是躲 `rt` 躲出来的。更干净的做法是把 join 声明到需要它的那个排序上（`Sorts` 从 `map[string]string` 变成 `map[string]Sort{Expr, Join}`），FROM 就能保持只有主表 |
| 测试覆盖 | `internal/vndb`、`internal/api/query`、`internal/cache`、`internal/dump` 有测试；七个类型包、`db`、`importer` 没有 |
| 导入路径没有端到端测试 | 只有对假服务器的单元测试。上游索引真变了仍然要跑一次才知道——2026-09 那次就是这样发现的 |
| 用户服务：登录的计时侧信道 | 用户名存不存在可由响应时间区分。已记录，未修 |
| 用户服务：`is_admin` 没人用 | 库里有、边缘也传了 `X-Is-Admin`，但没有任何管理面读它 |

### 已量过、不是问题

- **深翻页**：`vn?page=2750`（OFFSET 65976，最后一页）11.7ms，比第一页还快。这个数据量下 PG 走索引就走完了，不需要 keyset 分页。数据涨 100 倍再说。
- **按标题/名字排序需要派生列**：不需要。曾据此加过 `vn.c_title` / `chars.c_name` / `releases.c_title` 三个派生列，后来实测撤销——一对一 join 在不用时零代价（108–141ms vs 无 join 的 131–150ms，噪声内），用时 70–116ms，比相关子查询（210–226ms）快。`staff` 本来就是这么做的。
