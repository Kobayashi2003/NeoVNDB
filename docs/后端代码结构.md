## 一、总览

NeoVNDB 把 vndb 官方 dump **原样镜像**进本地 Postgres，再在其上封装一层只读 HTTP API。

核心约束（决定了整个代码形状）：

- **本地库是一次 dump 的纯函数** —— 除 dump 内容外不存任何东西，重新导入即完全重建，因此没有迁移、没有增量更新逻辑。
- **不修改任何来自 vndb 的数据**，也不导入 user 信息、评论、单条投票（只保留聚合值）。
- **不依赖 Kana API**：运行时和导入时都不调用，仅在开发期用于人工对数。
- **镜像只存原件**：数据库里 `vndb.*` 是 dump 的逐字镜像，`data/images/` 是图片的逐字节镜像。数据库的派生物（`tags_vn_inherit` 等）可以整个删掉重建；图片**不做任何派生**，缩略图用 vndb 自己发布的（`cv.t`、`st`）。

### 数据流

```
dl.vndb.org/dump/vndb-db-latest.tar.zst
        │  internal/dump        下载 + 校验 + 流式解 tar
        ▼
   tar 内的每张表（TSV）
        │  internal/importer    列改写（v17 → 17）后以 COPY text 灌入
        ▼
   schema vndb_next            ← internal/db/ddl/*.sql 建表
        │  internal/db/derive   算 dump 不导出的东西（分数、闭包、搜索索引、c_* 列）
        ▼
   ALTER SCHEMA RENAME         ← internal/db/generation.go，事务内原子换代
        ▼
   schema vndb（线上）
        │  internal/db/sql → sqlc → internal/db/gen   静态查询
        │  internal/api/query                          动态筛选/排序/分页
        ▼
   HTTP :17031                  internal/api
```

**代次（generation）**：`vndb`（线上）/ `vndb_prev`（上一代，用于回滚）/ `vndb_next`（正在导入）。
Postgres 的 `ALTER SCHEMA RENAME` 可以进事务，所以换代是原子的，线上 schema 永远不会处于半写状态。**在线换代也安全**：rename 不改表的 OID，pgx 又默认缓存预编译语句，但 PostgreSQL 会在 schema 改名时让依赖它的缓存计划失效（psql 实测：同一连接、同一预编译语句、执行超过转通用计划的阈值，rename 后返回新表的数据）。

## 三、逐模块逐函数

### 3.1 `cmd/neovndb` —— 命令行入口

#### `main.go`

| 声明 | 职责 |
|---|---|
| `usage` | 帮助文本常量 |
| `main()` | 调 `run()`，出错时打印并以非零码退出 |
| `run()` | 按第一个参数分发到 `serve` / `images` / `import` / `update` / `db` / `trans`；配置与 Store 由各子命令自己装载（`images` 根本不开数据库） |
| `runDB(ctx, args)` | `db` 子命令的二级分发：status / init / check / promote / rollback / drop / verify |
| `status(ctx, store)` | 取 `Store.Status` 并排版输出：各代次、DDL 是否过期、表行数 |
| `initGeneration(ctx, store, code, dumpURL)` | 用内嵌 DDL 建一个空的 `vndb_next` |
| `promote(ctx, cfg, store, args)` | 先过 `inspect` 熔断（`-force` 可强过），再把 `vndb_next` 换上线；导入未完成时拒绝 |
| `rollback(ctx, store)` | 把 `vndb_prev` 换回来 |
| `drop(ctx, store, schema)` | 删掉指定代次；拒绝删线上那一代 |
| `verify(ctx, store)` | 跑 `Store.Verify` 并逐步打印结果 |

#### `import.go`

| 声明 | 职责 |
|---|---|
| `localCode` | 从文件名里抠出 `vndb-db-2026-08-19.tar.zst` 的日期，正则 |
| `runImport(ctx, args)` | 解析参数后交给 `importArchive` |
| `importArchive(ctx, cfg, store, file, promote, force)` | 在 `Store.Exclusive("neovndb import")` 里跑 `importLocked`：定时更新与手动 import/update 共用一把咨询锁，后来者直接报 "another run holds the lock"（`db.ErrBusy`）退出，不排队。锁属于会话，而连接池会复用会话，所以解锁失败的连接直接关掉，不还回池里 |
| `importLocked(...)` | 导入全流程：定位归档 → `CreateNext` → `load` → `Index` → ANALYZE → `Derive` → 统计派生表 → `FinishNext`。顺序是性能关键（先灌数后建索引，派生前先 ANALYZE）。带 `-promote` 时先过熔断，上线后按 `NEOVNDB_DUMP_KEEP`（默认 2，即线上与上一代的归档）删掉更旧的归档；删不掉只打印，不影响已上线的新代 |
| `load(ctx, store, path)` | 建 Importer、接进度回调、返回每表行数 |
| `resolve(ctx, cfg, file)` | 决定用哪个归档：给了路径就用本地文件（校验和从文件算），否则查上游最新版并下载；本地文件没有上游给的发布日期，用文件名里的日期代替（否则这一代没有发布日期，页脚只能显示代次号） |

#### `update.go`

| 声明 | 职责 |
|---|---|
| `runUpdate(ctx, args)` | 开库后调 `updateOnce` |
| `updateOnce(ctx, cfg, store, force)` | 查上游 → 与线上代次比 → 相同则什么都不做 → 上游更旧则**拒绝倒退**（那是镜像出问题的样子，导进去会丢一周编辑）→ 否则导入并上线 |

**定时和手动走同一段代码**，这是有意的：只在无人值守时跑的更新路径，出问题的时候没人能复现。定时由 `serve` 进程自己跑（见下），不依赖系统计划任务。

#### `check.go`

| 声明 | 职责 |
|---|---|
| `inspect(ctx, cfg, store, force)` | 读两代的行数、跑 guard、打印结论。有异议则返回错误阻止上线，`-force` 可强过 |
| `counts(ctx, store, schema)` | 读导入时记录的行数；派生表缺失时现场统计（旧二进制导入的代次没记过派生计数，否则会被误报成"从没派生过"） |

#### `serve.go`

| 声明 | 职责 |
|---|---|
| `runServe(ctx, args)` | 建 `api.NewServer`，取路由（`Routes(admin)` 把 `admin.Mirror` 挂在 `/admin/` 下，共用日志与 panic 兜底），交给 `api.Serve` 监听。定时更新与管理页的"Check now"是**同一个 `admin.Job`**，所以两者不会同时跑，页面也看得到定时那一轮的输出。`update.Schedule(NEOVNDB_UPDATE_FIRST_AFTER, NEOVNDB_UPDATE_EVERY, NEOVNDB_UPDATE_RETRY_AFTER, failed)` 按时跑这个 Job 里的 `updateOnce`，`failed` 负责记日志并判断这次失败值不值得提早重试（默认启动 10 分钟后第一次、之后每 24 小时；上游没新的就是一次小请求；手动导入正持锁时记 Info 跳过这一轮；连不上上游或下载失败（`errUpstream`）记 Warn，`NEOVNDB_UPDATE_RETRY_AFTER`（默认 1h）后重试，而不是等满一天；导入失败、熔断拒绝等其他错误重试也一样会失败，照常等满间隔）。放在 serve 里是因为读 API 总在跑，且换代对它是一个事务，读者立刻看到新数据 |

#### `images.go`

| 声明 | 职责 |
|---|---|
| `runImages(ctx, args)` | 起图片镜像（`internal/img`），`/admin/` 下挂 `admin.Images`；预取同样包成一个 `admin.Job`，定时与按钮共用，结果是 `img.Report`（库里有多少、盘上已有多少、这轮取了多少、还缺多少）。**供图不开数据库**：请求自己说明要哪张图，没有要查的，所以这个进程与代次切换无关，promote / rollback 都不用重启它。`crawl.Schedule(NEOVNDB_IMAGE_CRAWL_FIRST_AFTER, NEOVNDB_IMAGE_CRAWL_EVERY)` 按时预取（EVERY 为 0 即关），每轮临时连库读 `images` 表（`db/sql/images.sql` 的 `ImageRefs`），连不上就跳过这一轮，供图不受影响 |
| `runCrawl(ctx, args)` | `neovndb crawl [--limit n]`：手动跑一轮预取，`--limit 0` 取完所有缺的 |

#### `trans.go`

| 声明 | 职责 |
|---|---|
| `runTrans(ctx, args)` | `trans status` / `trans seed [file]` / `trans export [file]` 的分发；不给文件就用仓库里的 `internal/trans/init.json`（`defaultCorpus`）。seed 在同一事务里推进 `trans.revision` |
| `transStatus(ctx)` | 打印目标语言与译文库里短名（terms）、长文本（passages）各多少条 |
| `transSeed(ctx, path)` | 读语料文件（`trans.Corpus`，旧项目导出的格式：按类别的标签/特征名 + 长文本列表），**先全量校验标记再写**，一条不过整份拒绝 |
| `transExport(ctx, path)` | 把库里的语料（含管理页上的编辑）写回文件：先写 `.partial` 再改名。`Corpus.Encode` 的形式是稳定的（名字按键排序、长文本按类型+原文排序、不转义 `<>&`），库没变时导出不产生 diff。**第一次导出会把 init.json 整体重排一次**（旧文件是旧项目的插入顺序），之后只有真实改动 |

### 3.2 `internal/config`

#### `config.go`

| 声明 | 职责 |
|---|---|
| `default*` 常量组 | 监听地址端口、连接池上下限、连接寿命与超时、dump 目录与上游 URL 的默认值 |
| `Config` | 全部配置项 |
| `Load()` | 先读 `.env`（真实环境变量优先），填默认值，校验 `NEOVNDB_DB_URL` 非空 |
| `(*Config).Addr()` | 拼 `host:port` |
| `envString / envInt / envDuration` | 三个带默认值的环境变量读取器 |

**配置项清单见 `backend/vndb/.env.sample`**，那里是唯一权威（用户服务同理，见 `backend/users/.env.sample`；边缘的环境变量见根目录 `README.md`）。这里只记两件从名字看不出来的事：

- 限制项限制的是**工作量而非正确性**，所以是设置不是常量。**`0` 表示无上限**（当前 `.env` 里所有 `MAX_*` 和 `REQUEST_TIMEOUT` 都设成 0）。
- `NEOVNDB_CACHE_TTL` 是**内存上限而非新鲜度**——库只在换代时变，缓存条目在那之前一直正确。
- **所有定时任务的时间都是设置**：每个任务一对 `*_EVERY`（间隔，`0` 关闭）与 `*_FIRST_AFTER`（启动后多久第一次跑）。本服务两个：更新（`NEOVNDB_UPDATE_*`，在 serve 里）与图片预取（`NEOVNDB_IMAGE_CRAWL_*`，在 images 里）。两个 Go 模块不共享代码，`internal/schedule` 各有一份。

#### 上游索引的两个坑（2026-09 实测）

**① 索引页里两处名字会互相矛盾。** 页面上有两张表：「Latest versions」用**纯文本**写着 latest 应该指向哪个档案，「Files」里才是**链接**着的、真实存在的文件。dump 正在发布的当口这两者会不一致——实测「Latest versions」说 `2026-09-09`，但只有 `2026-09-07` 被链接，而 `2026-09-09` 确实 404。所以扫全文取最大值会选中一个不存在的档案，必须只认 `href`。

**② `describe` 不检查 HEAD 状态码的话**，一个只被登记、尚未发布的档案会变成"0 MB、发布于公元 0001 年"，真正的失败要拖到下载时才以一个说明不了原因的错误暴露出来。

### 3.5 `internal/db/guard` —— 换代熔断

一次导入可以在机械意义上完全成功却仍然是错的：截断的归档照样能解析，派生步骤的 join 匹配不到东西时**不写任何行也不报错**。而镜像库自己没有可违反的不变量——它有的是**前一代**。

| 声明 | 职责 |
|---|---|
| `Snapshot` | 一代在检查眼里的样子：代次代码 + 每表行数 |
| `Finding` | 一条不该上线的理由 |
| `Check` | `Name()` + `Inspect(live, next) []Finding` |
| `Guard` | 一组检查，`Default(maxLoss, derived)` 给出标准组合 |
| `Shrunk{MaxLoss}` | 某表掉了超过该比例。**vndb 只增不减**（条目是隐藏不是删除，而隐藏的根本不进 dump），所以任何实质缩水都意味着归档被截断或导入中途停了 |
| `Missing` | 线上有、新代次压根没导的表——导入提前结束的样子 |
| `Required{Tables}` | 指定的表不得为空。这是**专为派生步骤准备的**：一个匹配不到东西的派生查询没有别的痕迹 |

**为什么是接口而不是一串条件**：什么算可疑取决于数据。哪个部署额外导了别的东西、或者明知某张表就是会缩，就自己加一个或去掉一个。

行数来自导入时记录进 `import_info.row_counts` 的**精确值**，读回来不花钱。

实测（20260819 → 20260907 真实一周）：全部通过，**不到 1 秒**。反向（拿旧代次当新代次）被拦住并列出 7 条异议。

### 3.8 `internal/api/query` —— 七类型共用机器层

#### 三个核心概念

**字段表（`Table`）**：一个类型的字段面**和**每个字段怎么产生，声明在同一处。校验用的 `Registry` 由它推导，所以"声明了却填不出来的字段"不可能存在 —— `NewTable` 在启动时 panic。

**Source**：收整页而不是单行，批量是结构性保证 —— Source 里根本拿不到"当前这一行"，写不出 N+1。多个字段可以共用一个 Source（`title`/`alttitle`/`titles` 同一次 `vn_titles`），只跑一次。

**Target（继承）**：片段不列子字段，而是**指向另一个类型的名字**。合法子字段 = `Edge ∪ 目标类型的全部字段`。目标类型加字段，所有嵌套它的地方自动可见。类型图有环（vn→character→vn），所以 Target 是字符串，经 catalog 在请求期解析。

| `Field[T]` | `Kind` / `Row`（逐行纯函数）/ `Source` / `Subfields` / `Edge` / `Target` / `Num` |

|---|---|
| `ParseFields(cat, reg, maxDepth, value)` | 深度上限由调用方传入，来自配置 |
| `FieldDef` / `Registry` | 校验面。`children(cat)` = `Subfields` ∪ 目标类型字段 ∪ `Edge`（**边属性优先**） |
| `Selection` | 一棵树。`All` = 片段被单独点名，意为"目标的全部**列**"——不含嵌套片段，因为每个都要一次查询，且类型图有环不会终止 |
| `ParseFields` / `add` | 逐段下钻校验。`id` 在**每一层**都是隐式的 |
| `Cost` | 每层字段数 × 该层声明的 `Num`，逐层相加。照 Kana 的算法，上限 10 万 |

#### `limits.go`

`Limits` 结构（`PageSize` / `MaxPageSize` / `MaxIDs` / `MaxFieldDepth` / `MaxCost` / `MaxSearchTerms` / `MaxFilterNodes`）+ `DefaultLimits()`。**全部来自配置，0 即无上限。** `Parse` 把它记进 `Request.Limits`，后续阶段（如 `Page` 校验 id 列表长度、`SearchFilter` 校验词数、表达式校验条数）沿用同一份，不会各自为政；它也进缓存 key，否则放宽上限只会把先前的拒绝从缓存里再端出来。

#### `expr.go` —— `f=` 条件表达式

| 声明 | 职责 |
|---|---|
| `ParseExpr(text, budget)` | 递归下降解析成树。`,` 或、`+` 与、`!` 非、括号；值含逗号、加号、括号时用双引号（`\"` `\\` 转义），值内部的空格无需引号。`budget` 是整个请求共享的剩余条数（`Budget(n)` 生成，nil 无上限），嵌套里的条件从同一份里扣；另有一道固定的递归深度护栏 `maxExprDepth = 64`——那不是策略，是防止无上限时把本进程的栈交给查询串的作者 |
| `leaf` / `junction` / `negation` | 树的三种节点 |
| `(*Builder).Expr` | 编译成**一条**条件加进 builder |
| 括号作为叶子的值 | `release=(lang=en)`：括号连同里面的文字**整块交出去**，解析器不知道那是关于谁的条件，也不需要知道——由它所属的筛选在编译时去读。找配对括号时**跳过引号内的文字**（含 `\"` 转义），所以 `producer=(search="a)b")` 不会在引号里的 `)` 处截断 |
| `leaf.compile` | 查该类型自己的筛选表，用一个共享 `Args` 的子 builder 跑它，取回条件。**所以新加的筛选不必改这里就能在表达式里用**；`!=` 编译成 `NOT(...)`，于是每个筛选都白得取反；`id` 明确拒绝——它跳过分页，不是条件 |

逗号的含义与从前一致：参数 `lang=en,fr` 是一个筛选两个可接受值，`f=lang=en,lang=ja` 是两个叶子取或，同一个问题同一个答案（实测均 58,459）。在 `f=` 里要把列表当**一个值**，得加引号：`f=lang="en,fr"`；不加引号的 `f=lang=en,fr` 会把 `fr` 当成第二个叶子而报错。

#### `page.go` 的 `searchRank`（`sort=searchrank`）

只看**匹配上的那些标签**，每个实体取最高分：

| 项 | 分 |
|---|---|
| 标签与整个查询（规范化后）完全相等 | +100 |
| 标签以查询开头 | +50 |
| 所有词都落在**同一个**标签里（而不是散在几个名字上） | +20 |
| 标签种类：主标题 / 别名 / 间接（发行版标题等） | +15 / +10 / +5 |

前三项（相等、前缀、同一标签含全部词）按标签种类**打折**：主标题 ×1、别名 ×0.7、间接 ×0.4。否则一个恰好以查询开头的别名会与以查询开头的标题同分——实测搜 VN `key` 时，别名 `keyorina` 的《夜明け前より瑠璃色な》和经由 "Key … Memorial Box" 发行版间接命中的 CLANNAD 排在了 Keynote 前面；打折后标题以 key 开头的作品居前。
| 与查询的 trigram 相似度（0–1） | ×10 |
| 人气（`PageSpec.Popularity`：VN 票数、标签/特征的条目数），`ln(1+n) × 2` | 最热门约 +20 |

人气只在同档匹配之间起作用，压不过更好的匹配。同分时 **id 小者在前**（老条目通常是人们要找的那个），不随 `reverse` 翻转。

两处性能要点：查询的规范化写成**不相关的标量子查询** `(SELECT search_norm_term($n))`，数据库只算一次——参数绑定时规划器无法把它折成常量，写在相关子查询的 FROM 里会对每个被排序的标签重算一遍（实测 "ai" 从 4.8s 降到 0.43s）；词表同理先整体规范化。单个词时"所有词在同一标签里"就是"包含查询"，直接用 LIKE，免去逐标签展开词表。排序参数在复制 WHERE 参数（给计数语句用）**之后**才加入，编号接在筛选参数后面，`TestSearchRankOrder` 守着这一点。

#### `page.go` 的 `SearchTerms`

把搜索词按空白拆开（引号内不拆），每个词各出一条 `EXISTS` 并 AND 起来：词序无关，且**词越多越快**（每个词都在收窄结果）。

#### `catalog.go`

| 声明 | 职责 |
|---|---|
| `Catalog` | 类型名 → `Nested`。全部类型建好之后统一注册 |
| `Check` | 遍历所有 Target，名字对不上就返回 error —— 拼写错误变成启动失败，而不是某次请求 panic |

#### `filter.go` 的两条路

一个筛选要么**匹配**一个值，要么**比较**一个值，代码里分得很清：

- `Match(one)` 是匹配类的唯一写法——它自带列表展开（逗号）和"拒绝比较运算符"。`TextColumn` / `ArrayColumn` / `RelatedID` / `Related` 以及七个类型包里的自定义筛选全部由它构造。这样写是为了**下一个新加的筛选不会漏掉那个拒绝**：从前 `lang>=en` 会被当成一个叫 `>=en` 的语言去找，找不到，看起来像"没有结果"而不是像写错了。
- 比较类（`IntColumn`、日期、身高……）自己用 `SplitComparison` 把运算符拆下来。

`Relation` 是可嵌套的关联（VN 的 release / developer / producer / character / staff / seiyuu，发行版的 vn / producer / developer / publisher，角色的 vn）：值是 id 就按 id 匹配（与从前同一句 SQL），值是括号就把里面的条件**用关联类型自己的筛选表**编译进那个 `EXISTS`。目标表按该类型的别名 join 进来；嵌套两层会重用同一个别名，SQL 作用域让内层胜出——这正是要的（每个筛选只谈自己那一类），但也意味着若有筛选去够外层的行会静默拿到内层。目前没有这样的筛选，真要有就得按层给别名编号。

`ExtLinkFilter(table, owner)` 是 v / r / p / s 共用的 `extlink=steam`：该条目在对应的 `*_extlinks` 里有指向该站点的链接。**不认识的站点直接报错**，而不是静默地什么都匹配不到。

`Related` 是标签/特征的连接匹配，可选最低分与剧透上限（`tag=g749:2.0:1`；特征没有分数，`trait=i568:1` 的数字是剧透）。不填时那两个条件**根本不出现在 SQL 里**，所以既有查询一字未改。声明了 `Join`（把标签/特征行按其筛选的别名接进来）的还接受括号形式 `tag=(search=school)`：括号里用标签类型自己的筛选编译，与 `Relation` 共用 `bracketed` / `Builder.nested` 两个小函数，没有第二份嵌套编译代码。

#### `page.go` / `convert.go` / `query.go`

与上一版一致：`Builder` + EXISTS 而非 JOIN、`Page`/`PageSpec`/`orderBy`/`SearchFilter`、六个公共值转换、`Request`/`Parse`/`ClientError`。

#### 字段取值方式分类

| 标签 | 含义 |
|---|---|
| `COL` | 本实体主表上的列，原样透出。改过名的会注明原列（`vn.c_length` → `length_minutes`） |
| `CONV` | 主表单列，换了个表示：单位、编码、拆行，或者把某种「没有」写法归一成 null。事实没变，形状变了 |

| `REL` | 指向另一个实体：目标类型的整个字段面 + 关系表自带的边属性 |
| `MADE` | 库里根本没存这个值，由 id 或配方拼出来——核对它等于核对那个配方 |

```go
Table: "vn LEFT JOIN vn_titles vt ON vt.id = vn.id AND vt.lang = vn.olang"
"title": "COALESCE(vt.latin, vt.title)"
```

三张被 join 的表主键都是 `(id, lang)`，而 join 把 lang 钉死成单值，所以每行最多匹配一行——**不放大行数**，"关系筛选用 EXISTS 不用 JOIN"那条规则（针对一对多）不受影响。`staff` 一直就是这么做的。

### 3.10 `internal/cache` —— 响应缓存

| 声明 | 职责 |
|---|---|
| `Cache` | `Get` / `Set` / `Name` / `Close` |
| `Key(generation, parts...)` | `neovndb:<代次>:<sha256 前 12 字节>`。**代次在最前面**，所以 `db promote` 之后上一代的 key 全部不可达，不需要手动失效。这里的"代次"实际是 `<代次>+t<译文版本>`（`api/cache.go`）：`trans seed` 推进 `trans.revision`，改了译文的旧缓存同样整批不可达 |
| `Nop` | 关闭时的实现 |
| `Memory` | 进程内 LRU（`container/list`），带 TTL。默认后端：单实例已经能拿到绝大部分收益 |
| `Redis` | 多实例共享时才值得那个依赖。读写失败只当没命中——缓存挂了是延迟问题，不是正确性问题 |

**key 在解析之后才算**（`query/key.go` 的 `Request.Canonical`），因为那时 `Selection` 已经是结构化的树、`Filters` 已经是 map，都能规范排序。所以 `fields=a,b` 和 `fields=b,a` 是同一条。`Limits` 也进 key —— 放宽上限之后，之前被拒的请求应该重新放行，而不是从缓存读回旧的错误。

接在 `handlers.go` 两个 handler 里，**不接在 resolver 内部**：嵌套请求内部的 `Objects` 各自缓存的话，失效逻辑没法推理。

**代次每次请求都读**，不做 TTL 复用。那次读是 0.12~0.18ms（1 行 16kB 的表），而缓存省的是 300ms。曾经用过 10s TTL，实测发现换代之后会出现一段窗口：有的类型已经答新代次、有的还在答旧 key 的缓存——不是"数据旧"而是"数据不自洽"。库不可达时退回上一次读到的代次，否则所有代次的 key 会塌到一起。

实测（`limit=100` × 4 个片段）：**305ms → 1.7ms**。

### 3.11 `internal/vndb` —— dump 自身的编码规则

纯函数，不碰数据库也不碰 HTTP。

#### `id.go`

| 声明 | 职责 |
|---|---|
| `TypeVN … TypeTrait` | 七个类型名常量 |
| `prefixes` | 类型名 → 单字母前缀（v/r/c/p/s/g/i） |
| `KnownType(name)` / `Types()` | 类型是否已知、全部类型 |
| `FormatID(entity, id)` | `17` → `v17` |

## 三·五、图片镜像（internal/img）

dump 的 `images` 表只有元数据（kind、num、宽高、内容投票），**一张图都没有**。所以镜像是残的，`internal/img` 补上剩下那半：importer 对数据做的事，它对图片做，区别只是按需单张而不是整包——46 万张里只有被看过的才值得存。

**它和后端其余部分的关系**

| | |
|---|---|
| 复用 | `internal/vndb`（`ImageURL`，分片规则两边必须一致）、`internal/config`（同一份 `.env`） |
| 明确不复用 | `internal/cache` —— 那是 API 响应缓存：内存/Redis、有 TTL、拿代际做键。图片缓存是磁盘、不过期、与代际无关 |
| 完全不碰 | `internal/api`。**供图不开 Postgres**：一次请求自带 `(kind, num)`，无需查表，因此它不知道什么叫代际，promote 和 rollback 对它没有影响。唯一的例外是预取（`crawl.go`）：它要知道 vndb 有哪些图，清单由调用方从库里读好再交给它，`internal/img` 本身仍不 import `internal/db` |

**一个目录，不做缩放**（2026-09-25 起）

```
data/images/           镜像。上游原字节，只增不改；路径与 t.vndb.org 同形
  cv/12/79412.jpg      封面
  cv.t/12/79412.jpg    vndb 自己的 256px 封面缩略图——只有宽于 256 的封面才有
  ch/…  sf/…  st/…     立绘（无缩略图）、截图、截图缩略图
```

此前按宽度（128/256/512）在本地缩放并另存一份；现在缩略图全部用 vndb 发布的，缩放代码、宽度白名单、像素上限、派生目录一并删除。URL 与磁盘路径同形，边缘用 Caddy 的 `file` 匹配器直接发命中的文件，Go 进程根本不醒。

**一次请求**

```
盘上有 → 边缘直出（绝大多数）
没有 → img.Server：single-flight 回源，逐字节落盘，返回
   └─ 要的是缩略图而上游没有（窄封面从来没有 cv.t）→ 给原图，不落假缩略图
```

**cv.t 的规则**：vndb 只给宽于 256px 的封面做缩略图（旧封面当年就按这个尺寸存，实测 256 宽的 cv/10039 没有 cv.t、315 宽的 cv/69839 有）。前端 `thumbnailURL` 按 API 给的宽度决定要不要 cv.t，预取也按 `images` 表的宽度只取存在的缩略图；镜像的"缺缩略图给原图"只是兜底。约 10.6 万张封面里 6.1 万张有 cv.t。

**原子写**（临时文件 + rename）：代理会直接从磁盘发文件，它没法问「这个文件写完了没有」。

## 三·五·五、相似作品（internal/db/similar）

vndb 没有"相似作品"，dump 里也没有可读的东西，所以每次导入时自己算，存进这一代的 `vn_similar(id, vid, score)`（列名与 `vn_relations` 一致；`similar` 是 PostgreSQL 保留字）。

- **向量**：一部作品是它的直接标签（`tags_vn_direct`，去掉 lie、只要正分），每个标签的权重 = 分数 × 稀有度（IDF，`ln(作品总数/带此标签的作品数)`）。只用内容（cont）与色情内容（ero）标签：技术标签（引擎、配音、长度）说的是怎么做的，不是像什么。
- **相似度**：余弦，再乘 `n/(n+6)`（n 是候选作品的标签数），免得只有两三个标签、恰好全中的作品排到前面。低于 0.08 的不要。
- **为什么是 Go**：两两相比要几十亿次乘法（实测按标签展开的配对有 38 亿）。做法是倒排索引：只让带过 3000 部以内作品的标签提出候选，按这些标签上的部分内积用一个 80 大小的小顶堆选出前 80，再对它们算精确余弦，留前 20。全库 6.1 万部、71 万个标签打分，实测 0.6 秒（含读写约 3 秒），按 GOMAXPROCS 并行。
- **去掉有关联的作品**：`vn_relations` 里任一方向有关系的（续作、FD、移植）不算，否则 Ever17 的前几名全是它自己的移植版与 Never7——这些侧栏的 Relations 里本来就有。
- **接入**：`importLocked` 在 SQL 派生之后调用 `similar.Build`，进度里显示为 `similar (Go)`；`vn_similar` 在 `db.Derived` 里，熔断照常检查它非空。API 是 VN 的 `similar` 片段（`REL vn_similar -> vn`，边上带 `score`），排序按分数。

## 三·六、译文（trans schema）

vndb 的标签与特征**只有英文**：没有"原文"可切回去，所以 `original` 开关在这两类上给出的是本项目自备的译文。这批数据不来自 dump，因此：

- 放在 **`trans` schema**，不在 `vndb` / `vndb_prev` / `vndb_next` 里。换代只 rename/drop `vndb*`，重新导入不碰它。
- **按文本内容做键**，不按 id：`trans.terms` 用规范化后的名字（`trans.Key`：空白折叠、去首尾、小写），`trans.passages` 用同一规范化结果的 sha256。这样新一期 dump 下来无需任何重解析——文本还对得上就命中，改过就不命中（宁可回落英文，也不显示过期译文）。
- DDL 幂等，`db.Open` 时建，因此新库无需额外步骤。

| 项 | 数量 |
|---|---|
| `trans.terms` | 5,726 |
| `trans.passages` | 6,361（其中约四十条是 vndb 改过原文后的旧版本，哈希已无人命中），约 3 MB |
| `trans.revision` | 一行计数器，每次 seed 加一，进响应缓存键 |

对当前镜像的覆盖率（2026-09-25 实测，按 API 实际查到的算）：**标签名 3,014/3,014、标签描述 3,011/3,011、特征名与特征描述均为 3,327/3,327，全部有译文**。

**管理页编辑**（2026-10-01）：`/admin/trans` 列出某类（tag / trait）的全部条目连同现有译文，在内存里过滤、分页（每类三千多条，按规范化规则在 Go 里查译文，不在 SQL 里重写一遍 `trans.Key`）；`PUT /admin/trans` 改一条名字或描述（描述过 `CheckMarkup`，空串即删除），同一事务里推进 `revision`，所以页面上立刻生效。编辑只进库：要保住它们得导出（管理页的 Export 或 `neovndb trans export`）并提交 init.json——库丢了而没导出，编辑就丢了。

**语料文件 `internal/trans/init.json`** 是唯一的一份（vndb 的 dump 里没有，重建不出来），所以进 git；`init_test.go` 逐条过 `CheckMarkup`，坏的编辑在 `go test` 就拦下。描述按原文哈希取译文，vndb 一改英文就对不上——补译时先对照旧译文改，而不是另起炉灶。

**`internal/trans/markup.go`** 守着唯一的硬约束：描述里的 `[url=..]`、`[b]` 等标记和 `g749` 这种裸 id 是地址不是语言，译文必须一字不差地带着它们（顺序可变，个数与内容不可变）。`trans seed` 先全量校验再写；有一条不过就整份拒绝，不写半份。实测 6,293 条译文全部通过，其中 4,342 条含此类记号。

API 侧是 tag / trait 上的 `translation` 片段（`lang` / `name` / `description`），以及 trait 的 `group_translation`；只查被选中的那一半。实测取译文与不取译文在 v17（203 个标签）上耗时无差别（62–65ms，噪声内）。

## 三·七、用户服务（backend/users）

**独立的 Go module，独立的数据库 `neovndb_users`**。不是镜像旁边的一个 schema——镜像的 schema 每周整个重建，账号跟着一起没了。没有 sqlc，查询都是手写的短 SQL；`schema.sql` 幂等，启动时执行。

├── cmd/users/main.go             启动、配置、扫会话与定时备份两个后台循环；`users backup` 立即备份一次；`users admin <name> [off]` 授予/收回管理员

├── internal/auth/

│   └── *_test.go                 账号规则、只读配置的那个 cookie 名、hash 往返

几处值得知道的取舍：

- **`/auth/verify` 是给边缘用的**，回 `X-User-Id` 与 `X-Is-Admin`。别的服务因此一行鉴权代码都不用写。
- **管理员**：`/auth/admin` 只对管理员回 204，其余 401/403；边缘在读 API 与图片镜像的 `/admin/*` 前用 `forward_auth` 问它。用户服务自己的 `/admin/*` 由 `adminOnly` 把关。第一个管理员只能用 `users admin <name>` 授予；管理页上对自己的账号不能设/撤/登出/删除（服务端也拒绝），免得把自己锁在门外。
- **只有 bcrypt**：旧服务迁来的账号只保留 kobayashi（已是 bcrypt），另两个删除后，读 Werkzeug scrypt 的兼容代码、登录时顺手重算 hash 的逻辑、同时读两个 cookie 名的兼容都已删除（2026-09-25）。
- **定时任务都在服务里**（`schedule.Every`，时间全是设置）：扫过期会话（`SWEEP_EVERY` 默认 1h，`SWEEP_FIRST_AFTER` 默认 1h）；定时备份（见下，`BACKUP_EVERY` 为 0 则整个关掉）。
- **定时备份**：服务每 `BACKUP_CHECK_EVERY`（默认 1h，启动后 `BACKUP_FIRST_AFTER` 默认 0 即立刻）看一次 `NEOVNDB_USERS_BACKUP_DIR` 里最新一份，比 `BACKUP_EVERY`（默认一周）旧就 `pg_dump` 一份，只留最新 `BACKUP_KEEP`（默认 8）份。按"最新一份的时间"判断而不是按启动时刻计时，所以常重启的服务也不会漏备。
- **`Items` 把整个收藏夹交出来**（上限 1000）给读 API 去排序/搜索——这个服务自己做不到，它不认识 VN 是什么。上限就是读 API 的 id 列表上限：1000 个 id 约 5KB 地址、22ms。
- **评分的清除是 DELETE**，不是 0 分："没有意见"不是一个低分。
- **上限都在 `.env`**：尝试次数与窗口、收藏夹页大小与整表上限。0 即无上限——`Items` 的 SQL 为此用 `LIMIT NULLIF($2, 0)`，否则 0 会被当成"一条都不要"。
- **限流分两把尺**：按来源地址、按用户名各计一次。一个攻击者换一堆地址会撞上后者，一个地址试一堆用户名会撞上前者。来源取边缘追加在 `X-Forwarded-For` 末尾的那一项——可信是因为这个端口只有边缘够得着。登录成功即清零。
- **`answer()` 只给收藏夹用**：它的两个具名分支说的都是"没有这个列表"，评分的 handler 因此直接走 `oops`。
- **类型字母与条目 id 的校验只有一处**：`validKind` 要求恰好一个类型字母（从前 `?type=` 用 `ContainsAny` 校验，`vx` 也能过）；`parseID` 要求字母后紧跟 1–9 开头的数字（`ParseInt` 本身会收下 `v+17`、`v017`）。`collections_test.go` 覆盖两者。

| ~~用户服务：`is_admin` 没人用~~ | **已解决**（2026-10-01）：管理页与 `/auth/admin` |

### 已量过、不是问题

- **深翻页**：`vn?page=2750`（OFFSET 65976，最后一页）11.7ms，比第一页还快。这个数据量下 PG 走索引就走完了，不需要 keyset 分页。数据涨 100 倍再说。
